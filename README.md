# 问渠 Agent（WenQu）

> 名字取自朱熹《观书有感》："问渠那得清如许？为有源头活水来。"——RAG 问答的本质，正是从知识源头取活水。

多能力 AI Agent 服务：**知识库语义问答（RAG，小说/文档通用）+ 数据分析工作台（长任务：阅读数据报告 / 小说文本分析）**，支持游客免登录体验与管理员模式，一条命令容器化部署。

```
┌────────────────────────── 浏览器 (Vue3 SPA) ──────────────────────────┐
│  对话 UI · 流式渲染 · 工具时间线 · 思维链折叠 · 知识库管理 · 深度思考开关 │
└───────────────────────────────┬───────────────────────────────────────┘
                          SSE 自定义事件协议 (text/tool/status/reasoning)
┌───────────────────────────────▼───────────────────────────────────────┐
│                        Node 服务端 (Hono + TS)                        │
│  ┌─ Agent Loop (AI SDK) ── stopWhen 护栏 + 滑窗上下文 + 断连取消       │
│  ├─ 工具层: searchNovel / getNovelInfo / queryChapters / analyzeTrend │
│  │           / generateReport                                        │
│  ├─ 两阶段深度模式: 快模型检索 → Z1 纯推理合成（思维链）               │
│  ├─ RAG: 多级摘要(章/段/全书梗概) + 向量召回 + rerank 精排             │
│  │        + T4 查询分解多路检索                                       │
│  ├─ pino 结构化日志: 模块子 logger + requestId + 分级过滤             │
│  ├─ MCP Server: stdio（宿主接入）+ HTTP（远程接入）双传输              │
│  └─ 会话隔离(游客/管理员) + 日限额/IP限频 + 错误分类降级               │
└───────────────────────────────┬───────────────────────────────────────┘
                                ▼
          SQLite(data卷) · 智谱 GLM · 硅基流动 bge-m3/reranker
```

技术栈：Node.js + TypeScript + Vercel AI SDK + Vue3/Pinia/Vite + Hono + SQLite(node:sqlite) + pino + MCP 官方 SDK

## 功能特性

- **Agent 编排**：Agent loop + Function Calling 多工具自主路由；stopWhen 步数护栏；断连自动取消上游请求
- **数据分析工作台（长任务）**：与对话分离的一级页面，侧栏选分析对象发起任务（受理即 202 → 进度落库轮询 → 报告阅读/导出）。平台层 runner（状态机/步骤落库/取消/降级）与剧本解耦，加场景 = jobs/ 加文件注册一行
  - *阅读数据分析（dataAnalysis）*：确定性管线——取数 → 趋势/异常检测 → 问题章节 RAG 原文归因 → 模型合成；数据来自上传的 CSV/xlsx（自动映射 + 校验）或内置演示数据
  - *小说文本分析（novelAnalysis）*：模型驱动——确定性文本画像（字数/段落颗粒度/对话密度/人称，textService 全量扫描）打底，agent loop 带工具（查章统计/读原文/语义检索）按编辑标准研判（黄金三章/节奏/POV），可选关联阅读数据集交叉归因（显式指定优先 + 保守自动匹配）
- **RAG 知识库问答**：双切块策略（小说走章节感知切块、文档走段落模式自动降级）、bge-m3 向量化、rerank 精排（命中率@1 58%→75%，评测集驱动）、回答标注文档名+章节/段落出处
- **多级摘要体系**：章摘要/段落摘要与原文同池检索（全局问题命中摘要、细节问题命中原文），全书梗概聚焦时注入提示词——全书级问题（"讲了什么故事"）的答案锚点；T4 复杂问题先查询分解再多路检索
- **入库管道**：Web 异步任务（全局进度卡片、断点状态持久化、并发上限防限流踩踏）、内容指纹去重、分段耗时日志、失败自动回滚 + 启动自愈清理僵尸任务；摘要批量生成（4 章/次调用 × 3 并发，433 章书约 20 分钟）
- **深度思考**：三态路由（自动启发式/强制深度/强制快速）；两阶段架构——快模型检索、Z1 纯推理合成，思维链实时流式展示
- **多模型路由**：免费模型池（glm-4-flash / glm-z1-flash），模型名配置化，限流自动重试与降级
- **MCP 双传输**：同一工具能力以 Function Calling（进程内）与 MCP（stdio/HTTP）双通道暴露，接入 CodeBuddy/WorkBuddy 实测通过
- **分级权限**：游客免登录体验（会话按访客隔离、只读公开演示库）+ 管理员账号（多管理员，环境变量配置）+ 一键公开/私有切换
- **防薅护栏**：全站日限额 + 单 IP 限频 + 上传大小/格式校验 + 内容指纹防重复上传 + 异步入库失败自动回滚
- **可观测性**：pino 结构化日志（模块子 logger、requestId 贯穿、级别过滤），入库分段耗时打点到阶段
- **容器化**：多阶段 Docker 构建，数据卷持久化，`docker compose up -d` 一条命令上线

## 快速开始

```bash
npm install
cp .env.example .env   # 填入 ZHIPU_API_KEY（open.bigmodel.cn 免费注册）
                       # 可选：SILICONFLOW_API_KEY（RAG 向量化用）、ADMIN_USERS（启用管理员）
```

| 模式 | 命令 | 说明 |
|---|---|---|
| **完整服务** | `npm run server` | http://localhost:3001 ，前后端同源（部署形态） |
| 前端开发 | `npm run frontend` | http://localhost:5173 热更新（注意：dev 代理会缓冲 SSE，测流式体验请用 3001） |
| CLI 对话 | `npm run dev` | 终端直接对话 |
| 文档入库 | `npm run ingest -- <txt> <文档名>` | CLI 入库（小说/文档通用）；Web 端可在页面直接上传 |
| 检索评测 | `npm run eval -- [K]` | 跑标注集算命中率@K |
| MCP 服务 | `npm run mcp:http` | HTTP 传输（stdio 由宿主按 .mcp.json 自动拉起） |
| Docker | `docker compose up -d` | 构建镜像 + 数据卷 + 自动重启 |

## RAG 检索质量（评测集驱动）

```
评测集 32 条（《绍宋》433 章真实语料，跨 5 卷）
命中率@3 基线：94%（30/32）
```

未命中案例分两类：标注歧义（问题泛化到相邻章也可答，仲裁修标注）与真实漏召回（跨卷实体、语义距离远——是检索优化的靶子）。标注集：`data/eval-set.json`（问题 → 应命中章节；事件横跨多章时支持 `accept` 多答案）。跑分：`npm run eval`。改切块/检索策略前后各跑一次，用数字而不是感觉做决策。

> 历史基线（旧演示书 12 条小池）：纯向量 命中率@1 58% → +rerank 75%，rerank 收益在真实大池上更显著。

## 小说体量分级标准（T1-T4，自适应处理策略）

入库时按 `totalChars` 自动定级写入 meta，查询按级别路由。分级影响**处理管道**，不影响存储引擎（SQLite 统一，level 列区分节点类型）。

T3 ✅ / T4 ✅ 已全部落地，流程见下方「入库 → 向量化 → 存储流程图」。

| 级别 | 体量 | 入库动作 | 查询动作 | 阈值依据 | 实现状态 |
|---|---|---|---|---|---|
| **T1 微型** | < 3 万字 | 仅存全文（不向量化） | **全量塞上下文**，跳过检索——零检索损耗 | 3 万字 ≈ 6 万 token，占 128K 上下文 ~15%，留足历史与回答空间 | ✅ 已实现 |
| **T2 小型** | 3-20 万字 | 切块 + 向量化 | top3 + rerank | 全局问题开始需要检索，但单路向量够用 | ✅ 已实现 |
| **T3 中型** | 20-100 万字 | + 章摘要层（level 1） | 两级路由：全局问题走摘要层定位、局部走原文 | 全局类问题（主题/人物弧线）的答案分散全书，单块检索必然失效 | ✅ 已实现（摘要层同池检索） |
| **T4 大型** | > 100 万字 | + 段落摘要层（level 2）+ 查询分解 | 查询分解多路检索 + 多级摘要路由 | 检索延迟与摘要层自身规模同时到临界（见检索性能阶梯） | ✅ 已实现（pgvector 迁移按性能阶梯触发，未到阈值） |

定级原则：**阈值是待校准的初值**（T1/T2 分界用「全量塞 vs 检索」的答对率对比实验校准）；分级确定后不随会话变化，保证行为可预测。

### 与托管方案的对比（VikingDB 知识库 / 上下文数据库）

调研过火山引擎 VikingDB 的两条产品线：**知识库**（托管式 RAG：语义切片 → 混合检索 → rerank → 大模型回答一条龙，旗舰版还有 DeepSearch 多轮拆解检索）和**上下文数据库**（把上下文组织成虚拟文件系统，每个目录自动生成 L0 摘要 / L1 概览 / L2 原文，内容变化自底向上聚合重生成）。本项目手写的多级摘要管道与后者的 L0/L1/L2 设计**同构**：

| 环节 | VikingDB | 本项目 | 差异本质 |
|---|---|---|---|
| 切块 | 通用语义切片 / 自定义分隔符 | 手写章节感知切块（卷识别 + 全局章计数解耦） | 思路相同；本项目按「第X章」边界切、天然带章节溯源，对网文更准 |
| 摘要层 | L0/L1/L2 自动聚合，增量重生成 | level 0/1/2（原文/章摘要/段落摘要），入库时批处理生成 | 同构；它多增量演化，本项目层级固定三级、可解释可控 |
| 定级路由 | 无（统一管道） | T1-T4 按 totalChars 定级，T1 全文注入免检索 | 本项目独有，避免小文档白跑全管道 |
| 检索 | 混合检索（稠密+稀疏）+ 标量过滤 + rerank | 向量召回 + rerank，T4 多路去重终排 | 它多稀疏向量和标量过滤；规模上是托管集群（HNSW/DiskANN）vs SQLite 暴力余弦 |
| 查询分解 | DeepSearch（旗舰版付费） | 查询分解 + 失败回退单路 | 思路一致 |

不迁移的理由：托管服务按量付费（本管道零成本）、全托管后手写管道的作品集价值归零、网文章回结构手写切块更贴。反过来，VikingDB 是数据规模到性能阶梯顶点时的生产化备选（见 Roadmap）。
